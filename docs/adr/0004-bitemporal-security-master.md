# ADR-0004: Bitemporal security master

**Date:** 2026-08-01
**Status:** Accepted

## Context

ADR-0007 establishes that `security_id` is the durable join key and that tickers
are time-bounded attributes. This ADR decides how that time-bounding is actually
stored.

Security reference data changes, and there are two genuinely different questions
a consumer can ask about any change:

1. **"What was true on 2024-03-01?"** — valid time. FB became META on
   2022-06-09. A backtest running over 2021 data should see `FB`.
2. **"What did we believe on 2024-03-01?"** — system time. If a vendor
   misclassified a security as `CS` and corrected it to `ETF` six months later,
   a report we published before the correction used `CS`. Reproducing that report
   requires knowing what we held at the time, not what we hold now.

Collapsing these two axes is the single most common way a "point-in-time" claim
turns out to be false. A plain SCD2 table gives one axis and is routinely
described as if it gave both.

The distinction has teeth here. Look-ahead bias in a backtest is exactly what
happens when today's reference data is applied to yesterday's prices — and
because the result is a plausible-looking number rather than an error, nothing
surfaces it.

## Decision

**Store both axes explicitly, and never conflate them in a column name.**

**Valid time** comes from the vendor and lives in `raw.security_master` as
`list_date` and `delist_date` (Polygon supplies `list_date` and `delisted_utc` on
its ticker-details endpoint). These describe when the security itself was
tradeable.

**System time** is generated by the platform via a dbt snapshot, using
`strategy='check'` over the mutable attribute set. The snapshot produces
`dbt_valid_from` / `dbt_valid_to`, which mean *when this platform first and last
believed this row* — not when it was true in the world.

**Identity is anchored on FIGI, not ticker.** `raw.security_identity` maps a
durable `security_id` to an `identity_key`. When OpenFIGI resolves a composite
FIGI, the key is `figi:<FIGI>`; FIGI survives rebrands and ticker changes, which
is precisely the property required. When no FIGI is available, a **provisional**
identity is minted as `vendor_ticker:<source>:<ticker>` and marked as such via
`identity_kind`, so provisional rows are queryable and countable rather than
indistinguishable from resolved ones.

**Provisional identities are promoted in place.** When a FIGI is later resolved
for a provisional row, `identity_key` and `identity_kind` are updated but
`security_id` is not. Every foreign key stays valid and no history is rewritten.

**`raw.security_master` holds only the current vendor snapshot**, upserted on
`(security_id, source)`. It is deliberately not the history table — the snapshot
owns history. Keeping the raw table current-only is what keeps it consistent with
ADR-0002's rule that `raw` mirrors what the vendor most recently said.

An as-of-date query therefore has to pin both axes:

```sql
where valid_from  <= :as_of_date and coalesce(valid_to, 'infinity')  > :as_of_date
  and dbt_valid_from <= :known_at and coalesce(dbt_valid_to, 'infinity') > :known_at
```

## Consequences

Good:

- Backtests can be made genuinely reproducible: pin `known_at` and the reference
  data is frozen to what was believed then, regardless of later corrections.
- Ticker reuse and ticker changes are both representable without ambiguity,
  because identity is anchored on something that does not change when the
  ticker does.
- Vendor corrections become visible as new snapshot rows rather than silent
  overwrites.
- Promotion-in-place means resolving a FIGI months later is not a migration.

Bad:

- Every reference-data query needs two date predicates. Forgetting one produces
  a plausible wrong answer, not an error. This is the sharpest edge in the design
  and is why the API will expose as-of lookups through a helper rather than
  letting callers hand-write the join.
- dbt snapshots only capture what a `dbt snapshot` run observes. A change that
  appears and reverts between two runs is invisible. System-time granularity is
  the snapshot cadence, not real time.
- The provisional-to-FIGI promotion has an unhandled edge: if a provisional
  identity resolves to a FIGI that already exists under a different
  `security_id`, the two rows genuinely refer to one security and need merging.
  Detection is implemented (the unique constraint on `identity_key` rejects it);
  automatic merging is **not**, and would require rewriting fact-table foreign
  keys. This is a known, accepted gap.

Neutral:

- Valid time is only as good as the vendor's `list_date`/`delisted_utc`, which
  are frequently NULL for older securities. NULL is stored as NULL rather than
  being defaulted to an open interval that would silently overstate coverage.

## Alternatives Considered

**Plain SCD2 on system time only (dbt snapshot, no valid-time columns).** The
common approach and much simpler. Rejected because the resulting table cannot
answer "what was the ticker on this date?" for any change observed later than it
occurred — which is the normal case, since we start observing a security long
after it listed. It would let the platform *claim* point-in-time correctness
while quietly failing the case that matters.

**Full bitemporal modelling with range types and exclusion constraints.**
Postgres `daterange` plus a GiST exclusion constraint would enforce
non-overlapping intervals at the database level, which is the rigorous answer.
Rejected for now as disproportionate: dbt snapshots do not emit range types, so
it would mean hand-rolling the SCD2 logic and losing dbt's tested implementation.
Worth revisiting if overlapping intervals ever actually occur.

**Ticker as the identity anchor with no FIGI dependency.** Removes the OpenFIGI
rate-limit dependency entirely. Rejected for the reasons in ADR-0007 — it is
incorrect under ticker reuse, and the incorrectness is silent.

**Snapshot `strategy='timestamp'` on the vendor's `last_updated_utc`.** Cheaper
than `check`, and the documented dbt preference where a reliable update timestamp
exists. Rejected because Polygon's ticker-details timestamp advances on fields we
do not track, which would generate spurious history rows that look like real
attribute changes.
